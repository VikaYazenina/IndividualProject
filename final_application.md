**[ ContentHarvest ]**

“Персональный агрегатор контента”


**[ ПРОБЛЕМНОЕ ПОЛЕ ]**

Контекст. Целевая аудитория получает информацию из множества разрозненных источников. Каждый источник публикует материалы независимо от остальных, а единого инструмента для их сбора у пользователя нет. Основные акторы: молодые учёные и студенты 22-30 лет; активные спортивные болельщики и авторы спортивного контента 14-25 лет (аудитория из РФ/СНГ, интерфейс на русском языке).

Проблема.

У пользователя отсутствует единое место, где собираются новые материалы из выбранных им источников: для просмотра обновлений необходимо открывать каждый источник отдельно, что приводит к информационной перегрузке.
При ручном просмотре источников пользователь не получает уведомлений о новых материалах, поэтому часть публикаций остаётся незамеченной или замечается с задержкой.
Отсутствует личный архив найденных материалов: чтобы вернуться к ранее увиденной публикации, её приходится искать заново.
Ручной мониторинг источников требует времени, которое растёт вместе с числом источников.

Метрика(как буду подтверждать эффективность): будет проведен опрос ЦА-тестировщиков, основная метрика - среднее время, затрачиваемое на мониторинг источников в неделю(предпроектное исследование(замер текущего времени) - Т1, предоставляем тестировщикам доступ на пару недель, постпроектное исследование(замер времени с использованием сервиса) - Т2).
Ключевой показатель эффективности(KPI)=(T2-T1)/T1*100%
По выносимой гипотезе сервис позволит сократить временные затраты не менее чем на 30%(KPI ≤ −30%).
Доп.метрики: уровень стресса от информационной перегрузки по 5-балльной шкале

Способы обоснования проблемного поля:
* Количественное исследование: анонимный опрос в Google Forms, около 14 вопросов (закрытые вопросы, шкалы 1-5 и один открытый вопрос), выборка — не менее 15 респондентов из целевых групп.
* Проверка гипотезы: дневник мониторинга (ежедневно, 4 вопроса) и послепроектный опрос (около 14 вопросов) среди 6-10 тестировщиков.
1.  У целевой аудитории отсутствует единое место для новых материалов из выбранных источников: из-за изобилия разнообразного контента его сложно находить(информационная перегрузка)
2.  Нет гарантии, что важное обновление на ресурсе не будет пропущено
3.  Отсутствует личный архив для сохранения найденных материалов
4.  Мониторинг источников вручную отнимает много времени

**[ АППАРАТНЫЕ / ПРОГРАММНЫЕ ТРЕБОВАНИЯ ]** 

Продукт разрабатывается исключительно как веб-сервис под клиентские устройства c такими требованиями:
* Процессор: двухъядерный, от 1,5 ГГц (или эквивалентный мобильный)
* Оперативная память: от 2 ГБ
* Объём памяти: установка не требуется, для кэша браузера достаточно 50 МБ свободного места
* Видеокарта: встроенная графика с поддержкой аппаратного ускорения браузера, дискретная не требуется
* Операционная система: Windows 10, macOS 11, Ubuntu 20.04, Android 8.0, iOS 14 или новее
* Браузер: Google Chrome 90+, Mozilla Firefox 90+, Safari 14+, Microsoft Edge 90+
* Интернет-соединение: от 1 Мбит/с, ширина экрана от 360 пикселей

Требования к хостингу:
* Запуск приложения на Python 3.11 с постоянным хранилищем для файла базы данных (используется облако Amvera)
* Доступ к SMTP-серверу для email-рассылки
* Доменное имя с HTTPS: contentharvest.online


**[ ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ ]**

Программный продукт будет предоставлять следующие возможности:
1. Управление источниками сбора информации (RSS/Atom-ленты и HTML-страницы): добавление, отключение, удаление, ручная проверка
2. Автоматический ежедневный парсинг и сбор данных
3. Функция отложенного прочтения
4. Поиск и фильтрация материалов в веб-архиве
5. Категории источников
6. Формирование ежедневной рассылки с новыми материалами
7. Хранение материалов в веб-архиве с пометками «прочитано» / «не прочитано»
8. Экспорт архива в формате CSV
9. Аналитика потребления (сколько материалов собрано и прочитано, распределение по источникам)
10. Работа с аккаунтом: регистрация, вход и выход
11. Раздел «Помощь» с описанием действий пользователя

  
**[ ПОХОЖИЕ / АНАЛОГИЧНЫЕ ПРОДУКТЫ ]**

Анализ 2 программных продуктов, которые максимально приближены к заданному функционалу, показал, что:

* Feedly: бесплатный тариф ограничен 100 источниками и 3 папками(премиум-функции и имеют высокую стоимость); персонального email-дайджеста нет; не предоставляет инструментов для самостоятельного добавления сайтов без RSS; на русский язык не переведен
* Inoreader: бесплатный тариф ограничен 150 RSS-лентами; интерфейс перегружен для новичков
* NewsBlur: бесплатный тариф ограничен 64 сайтами; подписка на сайты без RSS-ленты («веб-ленты») доступна только на самом дорогом тарифе Premium Archive; поиск по сохранённым материалам платный

Недостатки аналогов, которых нет у ContentHarvest: ограничение числа источников, платный доступ к сайтам без RSS и к поиску, отсутствие в бесплатных тарифах ежедневной подборки новых материалов одним письмом. 


**[ ИНСТРУМЕНТЫ РАЗРАБОТКИ, ИНФОРМАЦИЯ О БД ]**

* Python 3.11, FastAPI, Uvicorn - язык и фреймворк (одно приложение для REST API и серверных страниц)
* Jinja2, HTML/CSS - шаблоны страниц и писем
* SQLAlchemy, SQLite - ORM и база данных. Выбрана табличная база данных, так как данные (пользователи, источники, материалы) связаны отношениями «один ко многим»; SQLite не требует отдельного сервера и подходит для первой версии, при росте нагрузки переход на PostgreSQL выполняется заменой переменной окружения DATABASE_URL
* feedparser, requests, BeautifulSoup - получение и разбор RSS/Atom-лент и HTML-страниц
* APScheduler, smtplib - ежедневный обход источников и отправка писем
* PyCharm - среда разработки
* Git/GitHub - контроль версий; GitHub Actions - автоматические проверки (тесты, сборка Docker-образа)
* Pytest, Ruff - тестирование и проверка стиля кода (PEP 8)
* Docker - контейнеризация; Amvera - хостинг

**[ ВОЗМОЖНЫЕ РИСКИ ]**

*	Нехватка времени: использование простых и проверенных технологий, следование планированию, концентрация на приоритетных функциях
*	Сайты, подгружающие материалы через JavaScript: HTML-парсер их не видит, поэтому сервис сообщает пользователю причину ошибки и предлагает использовать RSS-ленту

*	Не хватит времени на освоение FastAPI и SQLAlchemy: у автора нет опыта серверной разработки, поэтому выбраны простые и документированные инструменты, а функции разработаны по приоритету (сбор, архив, рассылка, затем интерфейс и дополнительные возможности).
