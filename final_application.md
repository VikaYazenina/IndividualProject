**[ ContentHarvest ]**

“Персональный агрегатор контента”


**[ ПРОБЛЕМНОЕ ПОЛЕ ]**

1.  У целевой аудитории отсутствует единое место для новых материалов из выбранных источников: из-за изобилия разнообразного контента его сложно находить(информационная перегрузка)
2.  Нет гарантии, что важное обновление на ресурсе не будет пропущено
3.  Отсутствует личный архив для сохранения найденных материалов
4.  Мониторинг источников вручную отнимает много времени
   
Метрика(как буду подтверждать эффективность): будет проведен опрос ЦА-тестировщиков, основная метрика - среднее время, затрачиваемое на мониторинг источников в неделю(предпроектное исследование(замер текущего времени) - Т1, предоставляем тестировщикам доступ на пару недель, постпроектное исследование(замер времени с использованием сервиса) - Т2).
Ключевой показатель эффективности(KPI)=(T2-T1)/T1*100%
По выносимой гипотезе сервис позволит сократить временные затраты не менее чем на 30%(KPI ≤ −30%).
Доп.метрики: уровень стресса от информационной перегрузки по 5-балльной шкале


**[ ЗАКАЗЧИК / ПОТЕНЦИАЛЬНАЯ АУДИТОРИЯ ]**

Программный продукт может заинтересовать широкую аудиторию, поскольку рассчитан на проведение универсальных расчётов, однако необходимо выделить несколько групп пользователей, для которых существует свой тип настроек (профилей). Эти настройки будут влиять на функционал и интерфейс(внешний вид), тарифный план и возможность экспортировать результаты вычислений. К выделяемым группам относятся:

* Молодые ученые, студенты в возрасте 22-30 лет
* Активные спортивные фанаты(в основном инфлюенсеры, строящие свой контент на спортивной тематике) в возрасте от 14 до 25 лет
* Преподаватели вузов и научные сотрудники


**[ АППАРАТНЫЕ / ПРОГРАММНЫЕ ТРЕБОВАНИЯ ]** 

Продукт разрабатывается исключительно как веб-сервис под(клиентские устройства):
* устройства с доступом в интернет(ПК, смартфон, планшет и т.д.) любой ОС

    Требования к хостингу:

* Доменное имя с HTTPS: contentharvest.online


**[ ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ ]**

Программный продукт будет предоставлять следующие возможности:
* Управление источниками: добавление, редактирование, удаление, ручная проверка
* Автоматический ежедневный парсинг RSS/Atom-лент и статических HTML-страниц(по CSS-селекторам) с извлечением заголовка, ссылки, описания и даты
* Хранение материалов в веб-архиве с пометками "прочитано"/"не прочитано"
* Система категорий для источников
* Формирование ежедневной email-рассылки с новыми материалами
* Функция отложенного прочтения: материал возвращается в следующее письмо
* Экспорт архива в формате CSV
* Аналитика потребления: сколько материалов собрано и прочитано за период и по источникам
* Поиск и фильтрация: по ключевым словам в заголовке и описании; по категории, источнику, дате и статусам(полный набор через REST API, в веб-архиве: поиск по заголовку, категория, статусы)
* Регистрация и личные кабинеты: у каждого пользователя свои источники, архив и рассылка
* Раздел "Помощь" с описанием действий пользователя

  
**[ ПОХОЖИЕ / АНАЛОГИЧНЫЕ ПРОДУКТЫ ]**

Анализ 2 программных продуктов, которые максимально приближены к заданному функционалу, показал, что:

* Feedly: бесплатный тариф ограничен 100 источниками и 3 папками(премиум-функции и имеют высокую стоимость); персонального email-дайджеста нет; не предоставляет инструментов для самостоятельного добавления сайтов без RSS
* Inoreader: бесплатный тариф ограничен 150 RSS-лентами и 20 лентами-рассылками; интерфейс перегружен для новичков


**[ ИНСТРУМЕНТЫ РАЗРАБОТКИ, ИНФОРМАЦИЯ О БД ]**

*	Jinja2, HTML/CSS - интерфейс (серверные шаблоны)
*	Docker - контейнеризация (проверка сборки в CI)
*	Amvera - хостинг, домен contentharvest.online
*	Python 3.11, FastAPI, SQLAlchemy - язык и фреймворк
*	SQLite - база данных (файл в постоянном хранилище; при росте нагрузки переход на PostgreSQL заменой DATABASE_URL)
*	APScheduler, smtplib - ежедневный парсинг и email-рассылка
*	feedparser, requests, BeautifulSoup - получение и разбор источников
*	Pytest, Ruff - тестирование и проверка стиля кода
*	GitHub Actions - организация CI (тесты, проверка стиля, сборка Docker-образа)

Отличия от первоначального плана: вместо PostgreSQL, Celery и Redis использованы SQLite и APScheduler (проще для MVP, один процесс), Sentry и Playwright не потребовались.
